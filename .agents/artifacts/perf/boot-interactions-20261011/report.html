Fix candidates, in order of evidence

  1. Panel layout and repeated camera fitting. First-radio layout reached 128 ms in the desktop 4× trace. Measure stable panel bounds and avoid repeating identical framing work. Preserve the approved motion.
  2. Cold radio audio setup. First focus callback took 11–33 ms normally and 47–61 ms at 4×; repeat is much smaller. Prepare immutable noise data earlier while preserving gesture-based audio resume.
  3. Boot canvas texture uploads. Diagnostic uploads total 682–693 ms over boot, versus 26–29 ms over return. Test upload cadence/redundancy while retaining full-rate camera motion; cache text metrics afterward.
  4. First hover graphics. Five additional programs link on first hover; reflection costs roughly 29–35 ms in CPU samples. Warm those variants in existing small preparation batches; this explains part of the hitch.
  5. Rapid re-selection. Camera blend retreats for 3–4 sampled frames after a 100 ms BACK/reselect. Cancel the old focus-blend tween before starting its replacement. This small patch is proposed, not applied.

Input: regular scripted selections registered. An unexplained lost physical tap is not reproduced. Rapid re-selection also registers, but briefly keeps moving away before approaching again; it is not confirmation of the user’s uncertain missed clicks.

Practical limits

Fresh isolated profiles, ordinary audio/autoplay policy, real CDP mouse/touch dispatch, no network throttle. The panel probe performs style reads; a control omits them. Traces and CPU/GL diagnostics add overhead. Local station endpoint and live iframe timing differ from deployed CDN conditions. Lower-DPR did not consistently improve gaps. The no-style-probe control still stutters on first focus (142–190 ms max gaps). Cold START before radio interaction has 24.7 ms p95 / 75.7 ms max at 4×. Stream status reaches playing after about 2.0–2.6 seconds. CPU throttling cannot stand in for a phone GPU.
