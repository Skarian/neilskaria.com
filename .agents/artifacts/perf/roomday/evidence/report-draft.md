# Room daylight-map resolution test

Keep A (1024) for this performance goal. Neither shrink removes the blocking upload. B worsens mobile median TBT by 76.7 ms. C cuts its room-day task substantially but improves mobile median TBT by only 7.2 ms (1.4%), raises desktop TBT by 17.5 ms, and is 178.0 ms slower to START-ready on the phone median. B is 11.5 ms slower. Neither satisfies the requested no-slower-ready condition in this cohort. The sample does not establish a statistically reliable deployed gain.

## Root cause and the cheaper probes

The ~170 ms call is a native upload/driver synchronization stall occurring during texSubImage2D, rather than a unique format or mipmap cost of room-day. In three alternating original-order / room-first pairs, room-day goes from 242.4 / 166.5 / 108.6 ms to 3.7 / 4.0 / 8.7 ms; bed-day, now fifth, takes 112.0 / 108.7 / 161.1 ms. All maps keep their original resolution and pixels. This experimentally shows upload-order dependence; it does not identify the internal Chromium/ANGLE/AMD trigger or prove a particular staging-buffer capacity. The first baseline props-day capture also has a 153.9 ms cold wait; it is retained.

All six 1024 lightmaps are opaque three-channel WebP, decoded to ImageBitmap and uploaded using the same THREE RGBAFormat (1023), UnsignedByteType (1009), sRGB color space, LinearMipmapLinear minification (1008), Linear magnification (1006), and generated mipmaps. Wall-day/wall-lamp do not incur the large baseline wait. The measured synchronous generateMipmap call is roughly 0–0.1 ms; GPU work from earlier commands can still be what a later upload waits for. Native GPU timing and driver tracing were not available, so shader backlog versus transfer-memory reuse remains unresolved.

A per-upload flush probe reused the existing upload/yield loop and kept all pixels/resolutions. Room-day still took 92.5 / 111.6 / 97.7 ms. This is screening evidence only: no full Lighthouse/readiness cohort, no retained D, no claim of a qualifying engine fix. The previously documented pre-shader flush/finish and GPU-backed bitmap probes also failed. These order and flush checks were completed before packing smaller maps. All instrumentation and probe source changes were restored after builds.

## Lighthouse

Lighthouse 13.5.0, Chrome 154 at the requested executable, --use-angle=vulkan --enable-gpu, Radeon RX 590 (ANGLE Vulkan 1.3.260 / AMD proprietary driver). Four mobile and two actual desktop-config runs per variant, fresh browser profiles. Order for each round: A/B/C, C/B/A, A/B/C, C/B/A; desktop only in rounds 1 and 2. No builds, lint or other task CPU work overlapped the cohort. All 18 counted runs reached START, had a drawn room screenshot, and no runtime/WebGL failures. Every screenshot was inspected in rendered-runs.png. A .glb.br 404/fallback and a favicon 404 are common to all local runs and retained in console/network evidence.

Capture-only CDP hooks label blobs/bitmaps from their asset filenames and directly time each texSubImage2D; identical hooks run on every variant. No production engine instrumentation in counted builds. Lantern durations below are linked simulator CPU-node durations from the same long-tasks-diagnostic simulation used by Lighthouse, not observed time multiplied manually. They are complete containing tasks, not the native call alone. Linking uses the mark callTime inside the task: one C run has a rounded startTime mark 20 microseconds before its actual task. This correction is in the saved reproduction script. The simulated long-task diagnostic and total TBT metric have different windows/weighting; the long-task value is not a direct subtraction from TBT.

## Validation and limits

Pack runs succeeded and both commits were checked for their exact two-file scope. Vite client/server production output compiled. Vercel deployment packaging hit the known Windows symlink EPERM even after approved execution outside the sandbox; local preview output is complete, but deployment packaging is unverified. No deploy was attempted. The T3 collaborative preview is unavailable in this environment (status and open both explicitly report no automation host), so the authorized Chrome/Vulkan harness was used for captures.

The first visual attempt used stale capture output after a harness argument error and was terminated; it generated no valid comparison images and is excluded. Corrected visual builds were repeated. The initial diagnostic-only CDP harness inherited debug ports in 9500–9899 from the earlier harness; all counted measurements and visual captures use port 4298, and every local server uses 4290. Port 5174 was never used or inspected. This initial debug-port deviation is recorded rather than claimed compliant.

Exact GPU/ANGLE internals, a causal driver threshold, physical-device visual quality, a deployed score change and deployment packaging remain unverified. No full D Lighthouse cohort was run because order only relocated the wait and flush retained a large stall.

Reproduction scripts, LHRs, linked tasks, traces, full native screenshots, render confirmation sheet, map hashes, and diagnostic probe data are under evidence/. JSON traces and artifacts are gzipped. Browser profiles/cookies and output snapshots are excluded. Build snapshots and raw scratch remain in %TEMP%/impl/roomday.
