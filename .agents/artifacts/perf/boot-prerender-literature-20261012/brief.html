Evidence brief · 12 October 2026 · Research only

Pre-rendering can remove live Canvas2D text work. Blender export alone does not remove runtime rendering or prove a performance fix.

The strongest next prototype is a small, offline glyph atlas that the GPU draws directly. This recommendation is an architectural inference, not a benchmark result.

What the device evidence establishes. The supplied boot uses a 960 × 640 canvas for four seconds. It measures and paints text each frame, then marks the CanvasTexture dirty on every powered frame. GSAP separately controls the camera and GBA movement. The text and domain stay fixed.

On Android Chrome 154 / Adreno 740, historical text intervals averaged 35–39 ms. One willReadFrequently:true capture averaged 16.7 ms, with a smoother user report. Solid-fill returns also improved. These cross-session results do not establish causality or isolate font drawing. The control retains a possible +176 ms room-create-to-ready increase and one 118.9 ms handoff gap. Candidate d82230a remains rejected. None of the three options below has a device benchmark.

What glTF actually exports. Blender converts recognized material nodes into glTF data. It does not automatically render an arbitrary screen shader into a movie. Core glTF stores static image textures and transform/morph keyframes. It neither serializes a JavaScript CanvasTexture producer nor defines playback scheduling. Animated PNG content does not become a portable screen animation. [1] [2]

The current online Blender manual lists KHR_animation_pointer. That extension can animate mutable properties, including material factors, when the exporter and reader support them. It does not bake arbitrary shader nodes, fonts, or changing canvas pixels. Thus, “glTF cannot animate materials” is too broad. Exported letter meshes still need runtime animation and drawing. A rendered movie or frame sequence needs a separate playback path. [1] [3]

Skipping should directly select the final app state. Check compression, colour, fine strokes, and transparency. [6] [7]
Complete frames → resident atlas / sequence
Upload all frames once, then select a frame with texture coordinates or an array layer. One screen draw can sample the selected frame.		 Removes repeated uploads only while frames remain resident. Loading every frame moves decoding and upload cost into first use. Streaming reduces residency but restores recurring upload work. Texture dimensions need device limits. File compression does not imply equally small GPU storage. [5] Once resident, a frame index supports skip, replay, reverse, and GSAP time selection. Motion remains discrete at the authored frame rate. Lossless frames preserve the authored raster detail. Packing needs protection against sampling adjacent frames.
Static glyph / word atlas → GPU quads
Upload fixed glyph images and layout once. A shared text batch draws quads. Time and colour inputs drive transformations, glint, and fade. No canvas repaint or recurring pixel upload occurs.		 One image decode/upload, small geometry, and shader first use remain. GPU drawing and blending still cost time. Atlas batching reduces draw submissions. Cost follows atlas dimensions and visible glyphs, rather than four seconds of stored frames. [5] A shared boot time supports deterministic skip, replay, and reverse. Independent letter motion requires glyph regions, not only a whole-word image. Fixed masks remove runtime font measurement. Authoring must preserve font metrics, filtering, and the original motion.

Storage arithmetic, not measured allocation. One uncompressed RGBA8 frame uses 960 × 640 × 4 = 2,457,600 bytes, or 2.344 MiB. Four seconds at 30 fps require 120 frames, or 281.25 MiB. At 60 fps, 240 frames require 562.5 MiB. These figures exclude padding, mipmaps, CPU copies, and driver overhead. GPU compression changes the figures. Video file size depends on encoding. A glyph atlas stores each required shape once. Its actual dimensions and compressed bytes remain unknown.

Shared constraints. Blender typography and colour output need visual comparison with the current screen. Matching font names alone is insufficient evidence of matching pixels. Every option needs an application-controlled blend to runtime endColor. Powered returns should use that solid screen state without canvas repaint or dirty flags. Replacing only the four-second text segment leaves the recurring solid-fill path intact. Keep camera and GBA motion under their existing GSAP control.

One next prototype. Test an offline alpha atlas of the moving letters plus the fixed domain, with precomputed layout. Draw batched glyph quads directly in the GBA screen plane, clipped to its bounds. Use the existing boot time for shader motion, colour, glint, and fade. Keep the existing background with runtime endColor. Target one shared text batch. Do not add an intermediate render target.

This removes both repeated text rasterization and repeated canvas transfers, including powered returns. It introduces neither a video clock nor hundreds of frame textures. Unlike d82230a, it never repaints cached masks into a canvas. It does require shader and fidelity work. Generate the atlas offline. Do not generate frames, measure fonts, prepare panels, or add hidden warm draws during startup. Resource loading and first use still count as costs.

Acceptance measurements for that prototype. Compare it with the current canvas control in five alternating cold trials per variant on the affected phone. Include first boot, replay, and one powered return in each trial. Use the same display rate, build conditions, and cache policy. The historical default and rejected candidate are not acceptance baselines.

  • Record navigation-to-START, room-create-to-ready, first activation, and pre-START long tasks. Reject a repeatable increase beyond control variation. Do not conceal preparation before START.
  • For the current 60 Hz conditions, target approximately 16.7 ms mean intervals and p95 ≤20 ms during text and powered returns. Require no ≥42 ms interval in those phases. Record handoff maxima separately and reject a recurring >50 ms gap.
  • Record transferred bytes, decoded texture allocation estimates, first upload, and shader first-use time. Check zero recurring CanvasTexture uploads for boot and solid returns. Do not label JavaScript heap size as GPU memory.
  • Compare synchronized screen recordings for font edges, spacing, glint, colour, and the final fade. Check skip, replay, reverse, and GSAP alignment within one display interval. Retain the simpler control if the prototype provides no material benefit.

Evidence limits. Documentation supports mechanisms, not an expected speedup on this phone. VideoNG dates to September 2021. Its overlay and power examples concern browser video presentation, not this WebGL texture path. The core glTF document dates to 2021 and needs the later pointer extension caveat. Current Three.js and MDN pages do not establish the behaviour of this app’s installed versions. The Blender 5.4 online manual is documentation evidence, not an installed-exporter test. Its indexed primary text was accessible, while direct fetches returned HTTP 402. No neural-video papers or secondary performance anecdotes support this recommendation.

Eight primary sources and exact supporting sections
  1. Blender online manual, glTF 2.0 (5.4). “Exported Materials” and “Extensions.” Recognized node conversion and listed KHR_animation_pointer support.
  2. Khronos glTF 2.0 specification. §2.6, §3.8.3 “Images,” and §3.11 “Animations.” Core image formats, ignored PNG animation, and application-owned playback.
  3. Khronos KHR_animation_pointer. “Overview → Motivation / Operation” and “Extension Usage.” Mutable properties and the required reader support.
  4. Three.js VideoTexture. “Code Example,” “generateMipmaps,” and “update().” Direct HTMLVideoElement input, default mipmap policy, and automatic texture updates.
  5. Mozilla MDN, WebGL best practices. “Batch draw calls,” “Understand system limits,” “Consider compressed texture formats,” and “texImage/texSubImage uploads (esp. videos) can cause pipeline flushes.”
  6. Mozilla MDN, requestVideoFrameCallback(). “Parameters” and “Description.” mediaTime, presentedFrames, processingDuration, video cadence, and synchronization limits.
  7. Mozilla MDN, HTMLMediaElement.playbackRate. Opening description and “Browser compatibility.” Negative playback rates lack widespread support.
  8. Chromium, Deep-dive: VideoNG. “Some terms and layout,” “So many bits,” and “Rendering.” Decode paths, transfer costs, overlays, and frame selection.
